# Supabase : schéma et base locale

- **Ordre des migrations** (`migrations/`, appliquées par ordre de nom) : `20260506000000_baseline.sql` (schéma prod figé le 06/10/2026, état d'avant CM-69/CM-78), puis `20260812072300_drop_program_days_weekdays.sql` (CM-69), puis `20260912093000_session_sets_unique_set.sql` (CM-78), `20261006120000_cm58_auth_trigger.sql` (CM-58), `20261007090000_cm85_profiles_auth_fk.sql` et `20261007090100_cm85_duos_expand.sql` (CM-85 partie A : FK profils / comptes, duos à côté des couples). L'enchaînement complet = schéma prod actuel (une fois `ops/2026-10-cm85-partie-a.md` déroulé).
- **Base locale** (Docker requis) : `supabase start` démarre la stack, `supabase db reset` recrée la base depuis zéro (migrations puis `seed.sql`). URL/clés locales : `supabase status` (les clés n'apparaissent que si `gotrue` tourne : ne pas l'exclure avec `-x`).
- **CI (CM-98)** : le job `e2e` de `.github/workflows/ci.yml` fait exactement ça à chaque PR / push sur `main` (stack jetable, services inutiles exclus), build l'app contre la stack locale et lance les tests Playwright. Procédure locale identique : `tests/e2e/README.md`.
- **Données de test** : `seed.sql`, fictives (comptes Auth `toi@coach-en-muscu.test` / `elle@coach-en-muscu.test`, mot de passe de test `motdepasse-de-test`, créés AVANT les profils à cause de la FK CM-85 ; profils « Toi » `1111…` / « Elle » `2222…`, couple et duo `3333…`, compte « Solo » `4444…` hors duo avec son programme et une séance (CM-59, `solo@coach-en-muscu.test`), 12 exercices système, programme « Nos séances » avec « Haut du corps » et « Bas du corps », 1 séance terminée). Les e2e en dépendent (`E2E_PROFILE_NAME=Toi`, `E2E_SEANCE_NAME=Haut du corps` en CI) : renommer ces données impose de mettre à jour le job.
- **Vérifier sans Docker** : `scripts/check-baseline.mjs` (PGlite) rejoue tout et affiche des empreintes du schéma, comparables à la prod via `--print-hash-query`.
- **Règle désormais** : toute modification de schéma passe par un fichier `migrations/<horodatage>_<nom>.sql` committé, testé en local (`supabase db reset`), puis appliqué en prod. Plus de DDL direct dans le dashboard.
- **Attention prod** : ne jamais rejouer la baseline sur la prod (elle échoue volontairement si le schéma existe). L'historique `supabase_migrations` de la prod porte d'autres versions (14 entrées, dont `20260906140326` et `20260912211215` pour CM-69/CM-78) : avant tout `supabase db push`, aligner l'historique avec `supabase migration repair` (commandes exactes : `ops/2026-10-cm85-partie-a.md`, étape 4).
- **Vérifications SQL (CM-85)** : `checks/cm85_duos.sql` (2 membres max par duo, un seul duo par membre, FK profils / comptes, synchro couple ↔ duo, aucun droit `anon`), lancé par la CI après `db reset`, dans une transaction annulée. En local : `docker exec -i supabase_db_coach-en-muscu psql -U postgres -v ON_ERROR_STOP=1 < supabase/checks/cm85_duos.sql`.
- **RLS (CM-59)** : policies par duo (`migrations/20261010090000_cm59_rls_policies.sql`, 22 policies, toutes `to authenticated`) et droits au plus juste (`migrations/20261010090100_cm59_grants.sql` : rien pour `anon`, `authenticated` limité aux tables encadrées par une policy). L'app reste sur la service-role : ce SQL ne la concerne pas encore. Tests pgTAP : `supabase/tests/rls.test.sql` (comptes « Toi », « Elle » et « Solo », hors duo, du seed), lancés par `supabase test db` (base locale démarrée, après `supabase db reset`) ; la CI les joue dans le job `e2e`. Application en prod : `ops/2026-10-cm59-rls.sql` (dernière ligne `ok` = true, retour arrière en commentaire).
